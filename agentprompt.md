# MISTRAL (Remon Defense Agent)

## 1. Общая концепция

**MISTRAL** — это система активной защиты серверной инфраструктуры застройщика **Remon Development**. Основная задача — обнаружение аномалий, предотвращение DDoS-атак, эксплуатации CVE и внутренних уязвимостей кода. Агент работает параллельно с production-стеком (nginx, backend-сайта) и не нарушает его работу.

**Принцип работы:**
- В спящем режиме работают только лёгкие асинхронные мониторинговые скрипты.
- При обнаружении аномалии запускается нейронный агент через OpenRouter API.
- Нейронный агент анализирует ситуацию, принимает решения по нейтрализации угрозы и уведомляет информационного безопасника.

### 2.3. Структура сайта Remon Development — объект защиты

Сайт застройщика **Remon Development** — это крупный многофункциональный веб-портал с публичной частью, личным кабинетом, CRM-интеграциями и внутренними сервисами. Вот полная инфраструктура, которую защищает **MISTRAL**:

#### 2.3.1. Frontend (публичная часть)

**Публичный сайт** — основная витрина компании, генерирующая лиды и доверие клиентов.

| Компонент | Технологии | Что защищается |
|-----------|-----------|---------------|
| **Главная страница** | Next.js 15, React 19, TypeScript, TailwindCSS | От DDoS, deface, внедрения вредоносных скриптов |
| **Каталог квартир** (`/kvartires`) | Next.js SSR, REST API (`/api/apartments`) | От SQL-инъекций в фильтрах (city, rooms, price_min/max), XSS |
| **Проекты компании** (`/proekti`) | Next.js, статичный рендеринг | От XSS в описаниях, подмена данных о проектах |
| **Ипотечный калькулятор** (`/mortgage`) | React, встроенная логика на фронтенде | От подмены ставок, XSS в параметрах URL |
| **О компании** (`/about`) | Next.js, статичный рендеринг | От deface |
| **Новости / блог** (`/news`) | Next.js, SSR | От XSS в контенте, подмена публикаций |
| **Авторизация** (`/login`, `/register`) | Next.js + API `/api/auth` | Брутфорс, credential stuffing, OAuth-перехват |

**Критичные данные:**
- Цены и скидки на квартиры (финансовая целостность)
- Фотографии объектов (репутация)
- Персональные данные клиентов при регистрации (ФИО, телефон, email — 152-ФЗ / GDPR)
#### 2.3.2. Личный кабинет покупателя (ЛК)

**Авторизованная зона** (`/cabinet`) — доступна после JWT-авторизации. Самая чувствительная часть с точки зрения данных.

| Компонент | Риски | Защита MISTRAL |
|-----------|-------|----------------|
| **Авторизация / регистрация** | Брутфорс, credential stuffing, слабые пароли, атаки на OAuth (VK, Яндекс) | Скрипт B отслеживает аномальные попытки входа; rate-limit `express-rate-limit` |
| **Мои объекты (портфель)** | IDOR, подмена `userId` в запросах к `/api/users/me/apartments` | Скрипт D проверяет целостность прав доступа |
| **Ипотека и платежи** | SQL-инъекция, data leak | Semgrep сканирует SQL-запросы на инъекции |
| **Камеры онлайн** (`/cabinet` → камеры) | IoT-уязвимости, SSRF через `stream_url`, MITM | Скрипт C (проверка исходящих соединений, открытых портов) |
| **Чат с менеджером** | XSS в сообщениях, спам, флуд | Мониторинг частоты запросов к `/api/users/me/messages` |
| **Обновление профиля** | Mass assignment, подмена роли | Валидация полей на backend |

**Критичные данные:**
- Персональные данные клиентов (ФИО, телефон, email)
- Данные о купленных квартирах и ипотечных платежах
- История переписки с менеджерами
#### 2.3.3. Backend & API

**Серверная часть** — ядро бизнес-логики, интеграции с внешними сервисами.

| Сервис | Стек | Уязвимости | Контроль MISTRAL |
|--------|------|------------|------------------|
| **API Gateway** | nginx (стандартный, Alpine) | Rate limit bypass, path traversal | Скрипт C (сетевой), nginx config мониторинг |
| **Основной backend** | Node.js + Express + TypeScript | RCE, prototype pollution, XXE | Semgrep (SAST), логи ошибок |
| **Frontend-сервер** | Next.js 15 (SSR + static) | SSRF, XSS, RCE в Node.js | Trivy сканирование образов, Скрипт A (Docker watcher) |
| **База данных** | PostgreSQL 15 (Alpine, Docker) | SQL-инъекция, privilege escalation | Мониторинг процессов, аномальные запросы |
| **Загрузка файлов** | multer (Express middleware) | File upload vulnerability, path traversal | Скрипт D (File Integrity) |

**Внешние интеграции (API):**
- **VK OAuth** — авторизация через ВКонтакте (редирект на `oauth.vk.com`)
- **Яндекс OAuth** — авторизация через Яндекс ID
- **Telegram Bot** — бот для сброса пароля (`password_reset_tokens`), уведомления
- Банки-партнёры (ипотечные ставки, кредитные скоринги)
- SMS/email-шлюзы (уведомления клиентам)
- CRM (Bitrix24 / amoCRM / собственная)

Каждая интеграция — потенциальная точка SSRF, credential leak или supply chain атаки.
#### 2.3.4. Административная панель (админка)

**Внутренний инструмент** — фронтенд `/admin`, backend `/api/admin/*`. Доступ строго по JWT + `role=admin`.

| Модуль | API endpoint | Доступ | Риски |
|--------|-------------|--------|-------|
| **Управление пользователями** | `GET/PUT /api/admin/users/:id` | Админ | Подмена роли/статуса, privilege escalation |
| **Управление квартирами** | `GET/POST/PUT/DELETE /api/admin/apartments` | Админ | Подмена цен, скрытие объектов |
| **Управление проектами** | `GET/POST/PUT /api/admin/projects` | Админ | Deface карточек ЖК, фейковые проекты |
| **Управление новостями** | `GET/POST/PUT/DELETE /api/admin/news` | Админ | XSS в контенте, фейковые публикации |
| **Назначение квартир клиентам** | `POST /api/admin/users/:id/apartments` | Админ | Фейковые бронирования, кража объектов |

**Особенности:**
- Админка доступна через фронтенд-роут `/admin` — цель для брутфорса и попыток обхода `adminMiddleware`.
- Существует уязвимый debug endpoint `/api/admin/debug` (намеренно оставлен для диплома — агент должен его обнаружить и пометить как критичный).
- Любое изменение роли (`role`) или статуса (`status`) пользователя — критичная операция, требующая аудита.

#### 2.3.6. Критичные точки для MISTRAL

| Точка | Последствия компрометации | Приоритет защиты |
|-------|--------------------------|----------------|
| **nginx конфиг** | Полный отказ в обслуживании, редирект на фишинг | Критичный |
| **Backend код (API)** | RCE, утечка всех клиентских данных, подмена ДДУ | Критичный |
| **База данных** | Утечка PII, финансовых данных, компрометация всех сделок | Критичный |
| **Docker-контейнеры** | Container escape, lateral movement, майнинг | Высокий |
| **SSH / root доступ** | Полный контроль сервера, сокрытие следов | Критичный |
| **Логи (nginx, системные)** | Невозможность расследования, подмена evidence | Высокий |
| **Админка** | Подмена цен, кража базы, фейковые бронирования | Высокий |
| **Внешние API (банки)** | Финансовые потери, репутационный ущерб | Высокий |
| **CDN / DNS** | Deface, перехват трафика, фишинг | Средний |

#### 2.3.7. Регуляторные и репутационные риски

- **152-ФЗ** (РФ): утечка персональных данных клиентов → штрафы до 75 млн ₽.
- **Градостроительный кодекс**: целостность данных о ДДУ и разрешениях на строительство.
- **Репутация застройщика**: deface сайта или публикация фейковых цен → потеря доверия, отток клиентов.
- **Финансовые риски**: подмена реквизитов на странице оплаты → перевод денег мошенникам.

### 2.4. Совместимость MISTRAL с инфраструктурой

Агент работает параллельно с production-стеком (nginx, Next.js, Node.js/Express, PostgreSQL) и не нарушает его работу:

- **Docker-native:** все сервисы сайта запущены в Docker-контейнерах (`frontend`, `backend`, `db`, `nginx`, `certbot`). Агент мониторит Docker daemon и отслеживает неожиданные контейнеры.
- **No Redis:** сессии реализованы через JWT (access + refresh tokens), хранимые в PostgreSQL (`sessions`). Redis не используется — агент не требует его мониторинга.
- **No MySQL:** единственная СУБД — PostgreSQL 15 Alpine в Docker. Все SQL-запросы параметризованные (`$1`, `$2`...), но `express-rate-limit` и Semgrep всё равно проверяют аномалии.
- **Статические пути неактуальны:** вместо `/var/www/html` проект использует Docker volumes (`./frontend:/app`, `./backend:/app`). Агент мониторит изменения в этих volume и git-репозитории.
- **nginx стандартный:** без OpenResty, Lua-скриптов. Конфигурация в `nginx/nginx.conf` — агент отслеживает её целостность.
- **Certbot встроен:** автоматическое обновление SSL через Let's Encrypt. Агент проверяет срок действия сертификатов.
- **Логи агента пишутся в отдельный каталог `/var/log/mistral/`.**

## 3. Уровень 2: Асинхронные мониторинговые скрипты (Спящий режим)

### 3.1. Общие требования

- **Языки:** Python 3.11+ (основной), Lua 5.4 (для быстрых системных проверок), C++20 (для критичных по производительности модулей).
- **Парадигма:** полностью асинхронная (asyncio / libuv / собственный epoll/kqueue).
- **Нагрузка:** минимальное потребление CPU/RAM. Скрипты не должны добавлять >1% нагрузки в idle.
- **Разделение обязанностей:** каждый скрипт отвечает строго за свою зону.

### 3.2. Скрипт A: System Anomaly Watcher (Python)

**Обязанности:**
- Мониторинг системных метрик: RAM, CPU, load average, inode usage, disk I/O.
- Анализ `systemd` journals на ошибки, failed units, неожиданные рестарты.
- Проверка Docker daemon: неожиданные контейнеры, изменения образов, anomalous network exposure.
- Проверка других критичных демонов (nginx, ssh, database): неожиданные рестарты, аномальные child-процессы.

**Аномалии:**
- RAM выросла на >X% за Y секунд без объяснимой причины.
- Появился failed unit.
- Docker-контейнер запущен с неизвестного образа.
- Неожиданный порт открыт внутри контейнера.

### 3.3. Скрипт B: Root & Auth Watcher (Python / Lua)

**Обязанности:**
- Мониторинг активных сессий root и sudo.
- Анализ `/var/log/auth.log` / `journalctl _COMM=sshd` на неудачные и успешные входы.
- Отслеживание новых SSH-ключей, изменений в `/root/.ssh/`.
- Проверка подключений: кто подключён, с какого IP, как давно.
- Обнаружение входа с "левого" IP (whitelist-based + geo/rate anomaly).

**Аномалии:**
- Новый вход root с неизвестного IP.
- Множественные failed login attempts.
- Изменение authorized_keys.
- Сессия root без соответствующего ticket/approve.

### 3.4. Скрипт C: Network & Process Watcher (C++ / Python)

**Обязанности:**
- Мониторинг сетевых соединений (`/proc/net/tcp`, `ss -tan`).
- Обнаружение DDoS-признаков: резкий рост входящих соединений, SYN-flood patterns, аномальное распределение по IP/странам.
- Проверка запущенных процессов: неизвестные бинарники, процессы без родителя, скрытые процессы (cross-check `/proc` vs `ps`).
- Проверка открытых портов: появление нового listening-порта.

**Аномалии:**
- Количество ESTABLISHED соединений на nginx превысило порог.
- Обнаружен процесс с подозрительным именем/путём.
- Новый listening port без одобрения.

### 3.5. Скрипт D: File Integrity & CVE Watcher (Python)

**Обязанности:**
- Базовая проверка целостности критичных файлов: nginx configs, site code, ssh configs.
- Мониторинг появления новых файлов в web-root.
- Проверка версий критичного ПО (nginx, OpenSSL, Docker) на наличие известных CVE через локальную базу или API.

### 3.6. Скрипт E: Semgrep & Trivy Scanner (Python)

**Обязанности:**
- **Semgrep** — статический анализ кода сайта (SAST): поиск бэкдоров, SQL-инъекций, XSS, hardcoded credentials, опасных eval/shell паттернов.
- **Trivy** — сканирование Docker-образов и OS-пакетов на известные CVE (NVD база).
- Парсинг отчётов сканеров в единый формат JSON для нейросети.
- Отправка структурированного отчёта в Telegram-бот ИБ-специалиста.

**Режимы работы:**
- **Спящий режим:** сканеры не работают, скрипт только отслеживает `inotify`/`git` изменения в кодовой базе. При изменении — готовит триггер.
- **Ручная активация (рубильник):** ИБ-специалист или программист запускает полное сканирование через Telegram-бот или TUI. Результат сохраняется в `/var/log/mistral/scanner/`.
- **Автоматическая активация:** если монитор (уровень 2) обнаружил аномалию в web-root или Docker, сканер запускается для уточнения.

**Формат отчёта для Telegram:**
```
🔍 [MISTRAL SCANNER REPORT]
📅 Время: 2024-01-15 14:32:11 UTC
🎯 Тип: Semgrep + Trivy
⚠️ Severity: HIGH (3 findings)
и вырезка из кода (там чё-нибудь)

[Semgrep]
- file: ./backend/src/routes/auth.ts:123
  rule: typescript.lang.security.sql-injection
  message: Возможная SQL-инъекция в параметре email
  fix: Убедитесь, что используются параметризованные запросы (уже $1)
[Trivy]
- image: nginx:1.24.0-alpine
  CVE-2023-XXXX: OpenSSL 3.0.8 (CRITICAL)
  Рекомендация: обновить до nginx:1.25-alpine

📎 Полный лог: /var/log/mistral/scanner/scan_20240115_143211.json
🤖 Нейросеть может применить fix через рубильник.
```

**Сохранение для нейросети:**
- Все отчёты сканеров пишутся в `/var/log/mistral/scanner/`.
- Нейросеть в режиме "рубильник" может прочитать последний отчёт и сгенерировать патчи (`openai/gpt-5.1-codex`) или написать правила mitigations (`qwen/qwen-3-coder-next`).
- История сканов доступна для сравнения: "что было до / что стало после".

**Требования к ресурсам:**
- Semgrep запускается только на diff (изменившиеся файлы), а не на всю кодовую базу.
- Trivy сканирует только активные Docker-образы и при появлении новых layers.
- CPU/RAM нагрузка минимальна в спящем режиме (только inotify watchers).
## 4. Уровень 3: Нейронный агент (OpenRouter API)

### 4.1. Модели и назначение

Агент взаимодействует с **OpenRouter API** и архитектурно поддерживает интеграцию трёх моделей для разных задач. Однако по требованию заказчика (экономия средств на этапе развёртывания) **пока активна только одна — самая дешевая**. Переключение между моделями реализовано через конфиг `config/mistral.yaml` или рубильник — достаточно изменить `model_id`.

| Модель (OpenRouter ID) | Назначение | Статус |
|------------------------|-----------|--------|
| `openai/gpt-5.1-codex` | Базовый аудит кода, анализ логов, генерация простых патчей и скриптов. | **Активна (дефолт)** |
| `openai/gpt-5.2-codex` | Сложный анализ ситуаций, стратегические решения, генерация подробных отчётов для ИБ-специалиста. | Доступна через рубильник |
| `qwen/qwen-3-coder-next` | Быстрый анализ логов, написание правил iptables/nginx, скриптов реагирования, генерация WAF-правил. | Доступна через рубильник |

**Архитектурная готовность:**
- Весь код агента работает через единый OpenRouter client — смена модели = изменение одного поля `model` в JSON payload.
- Промпты для всех трёх моделей заранее подготовлены и протестированы.
- В будущем (по мере роста бюджета) можно активировать `gpt-5.2-codex` или `qwen-3-coder-next` без изменения логики агента.### 4.2. Сценарий активации

1. Монитор (уровень 2) обнаруживает аномалию.2. Монитор формирует JSON-слепок: метрики, выжимка из логов, PID, IP, временная метка.
3. JSON передаётся в нейронный агент.
4. Агент запрашивает **активную модель** (`openai/gpt-5.1-codex` по умолчанию, либо выбранную через рубильник):
   - **Стратегический анализ** (`gpt-5.2-codex`, если активна): "Что происходит? Оцени угрозу 1-10. Какие шаги предпринять?"
   - **Аудит кода** (`gpt-5.1-codex`): "Вот фрагмент кода/лога. Есть ли уязвимость? Какой патч применить?"
   - **Быстрые правила** (`qwen-3-coder-next`, если активна): "Напиши правило iptables/nginx conf для блокировки этой атаки."
5. Агент выполняет рекомендации (блокировка IP, рестарт службы, применение патча).6. Агент отправляет уведомление информационному безопаснику.

### 4.3. Действия нейронного агента

- **DDoS:** автоматическое создание rate-limit rules в nginx + iptables drop для top-offenders. Возможно включение Cloudflare/аналога API.
- **CVE-эксплуатация:** анализ затронутого сервиса, предложение временного mitigations (например, WAF-правило), дальнейший патч.
- **Внутренняя угроза (root):** мгновенная блокировка сессии, смена ключей/паролей, уведомление.
- **Аномалия кода:** `openai/gpt-5.1-codex` анализирует git-diff, находит backdoor или уязвимость, генерирует fix.

### 4.4. Ручное управление нейросетью — "Рубильник" ИБ-специалиста

Помимо автоматической активации по аномалии, у информационного безопасника есть возможность **намеренно запустить нейросеть** в любой момент.

**Интерфейсы рубильника:**
1. **Telegram-бот** — основной канал удалённого управления. ИБ-специалист отправляет команду, выбирает модель и задаёт задачу.
2. **Консольное GUI (Python TUI)** — минимальное cmd-формат приложение, установленное на сервере. Работает прямо в терминале, не требует графической оболочки. Позволяет выбрать модель и ввести промпт локально.

**Выбор модели:**
ИБ-специалист вручную выбирает одну из трёх нейронок:
- **gpt-5.2-codex** — для сложного анализа и стратегических решений.
- **openai/codex** — для аудита кода и генерации патчей.
- **qwen-3-coder-next** — для быстрого написания правил и скриптов.
**Формат ручного запроса (рубильник):**
ИБ-специалист указывает, что именно нейросеть или сканер должны выполнить. Примеры:

Запуск нейросети:
```
/model codex
/task Проверь ./backend/src/ и ./frontend/src/ на наличие бэкдоров, уязвимостей и hardcoded credentials.
Если найдешь — сгенерируй патч и покажи diff.
```

Запуск сканера (Semgrep/Trivy):
```
/scan semgrep ./backend ./frontend
/scan trivy image nginx:alpine
/scan trivy image node:20-alpine
/scan all               # полное сканирование
```
```

После сканирования скрипт E парсит результаты и отправляет структурированный отчёт в Telegram.
Нейросеть может быть запущена поверх отчёта для автоматического исправления:
```
```
/fix last_scan          # openai/codex читает последний скан и генерирует патчи
/mitigate last_scan     # qwen/qwen-2.5-coder-32b-instruct пишет правила nginx/iptables
``````
```

**Ограничения ручного режима:**
- Нейросеть **не имеет права отключать или перезагружать сайт/сервер**.
- Запрещено останавливать nginx, Docker, systemd-службы сайта, асинхронные чекеры-мониторы.
- Запрещено удалять или модифицировать логи агента.
- Все действия логируются и отправляются второму ИБ-специалисту (four-eyes principle).

**Цель:** показать, что агент способен обнаружить и нейтрализовать даже продуманную атаку, следуя которой я (тестировщик) буду действовать.

### 5.2. Как это работает

1. Врайтап содержит чёткий план атаки: путь эскалации, целевые файлы, техника обхода.
2. Я использую этот план для симуляции атаки на тестовой/стейджинговой среде.
3. Мониторинговые скрипты на уровне 2 должны засечь первые признаки (новый root-login, изменение файла, аномальный процесс).
4. Нейронный агент анализирует паттерн и **обрубает возможность продолжения атаки**:
   - Блокирует мою сессию.
   - Откатывает изменения.
   - Генерирует инцидент-репорт.
5. Это демонстрирует полный цикл: обнаружение → анализ → реагирование → отчёт.

### 5.3. Пример врайтапа (краткий)

## 10. База знаний агента — врайтапы и методики

Агент хранит у себя обширную базу данных врайтапов и методик пентестинга для распознавания атак по паттернам. Это позволяет нейросети не просто реагировать на аномалию, а понимать **контекст атаки** — какой шаг в цепочке kill chain сейчас происходит.

**Источники базы знаний:**
- PentesterGPT и аналогичные проекты с GitHub.
- Публичные write-ups с HackerOne, Bugcrowd, Exploit-DB.
- MITRE ATT&CK framework (сопоставление техник).
- Локальные write-ups, специфичные для инфраструктуры Remon Development.

**Как это работает:**
1. При срабатывании монитора агент получает не только сырые метрики, но и сравнивает паттерн с известными врайтапами.
2. Например: "Новый root-login + изменение authorized_keys + запуск nc" — агент распознаёт это как **шаги 2-4 из известного инсайдерского write-up**.
3. Нейросеть сразу понимает, что атака идёт по знакомому сценарию, и применяет заранее подготовленные контрмеры.
4. Это ускоряет реакцию и повышает точность — агент "учился" на публичных и приватных write-ups.
